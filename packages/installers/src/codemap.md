# packages/installers/src/

## Responsibility

Implementation of the installer system: the `Installer` contract (`types.ts`), the nine-IDE registry (`registry.ts`), the per-IDE modules (`claude-code.ts`, `codex.ts`, `copilot.ts`, `augment.ts`, `opencode.ts`, `gemini-cli.ts`, `cursor.ts`, `antigravity.ts`, `bob.ts`), shared filesystem primitives (`fs-utils.ts`), and the Windows `sh` probe (`windows-sh.ts`).

## Design

- **`types.ts`** defines `InstallContext` (`ideConfigDir`, `cliPath`, `nodeBin`, `dataDir` — `nodeBin` exists because Windows can't exec a raw `.js`, EFTYPE; plus optional `remote: { url, token }`, set by `apps/cli` when `settings.remote.url` is configured — installers then emit a URL-based MCP entry pointing at `<url>/mcp` instead of the local stdio spawn, while hook commands stay identical in both modes: the CLI decides at runtime whether to write locally or POST), `CaptureLevel` (`'full' | 'partial' | 'none'`, surfaced in `cavemem status` per issue #58), and the `Installer` interface (`detect`/`install`/`uninstall`, install/uninstall return `string[]` messages).
- **`registry.ts`** declares the `IdeName` union and the `installers: Record<IdeName, Installer>` map; `getInstaller` throws `Unknown IDE: <name>. Known: …`. `index.ts` re-exports the registry, the `windows-sh` API (`checkWindowsSh`, `resolveShDefault`, `WINDOWS_SH_MISSING_WARNING`), and `CODEX_TOKEN_ENV`.
- **`fs-utils.ts`** — `readJson` (fallback on missing/corrupt), `writeJson` (mkdir -p, 2-space, trailing `\n`), `shellQuote` (bare-token regex whitelist; backslashes deliberately excluded so MSYS-bash doesn't strip them from Windows paths — double quotes preserve them under both cmd.exe and sh), `deepMerge` (recursive over plain objects; arrays replaced wholesale).
- **`claude-code.ts`** (`capture: 'full'`) — hooks for all five events into `~/.claude/settings.json`, stripping prior cavemem entries (`isCavememHookEntry` matches `hook run <id>`) while preserving user hooks; when user hooks were preserved it backs the file up as `<path>.pre-cavemem-<Date.now()>`. Hook commands stay plain command strings (no `args` exec-form / `shell` field — see in-source #57 comment: an unsupported field silently ignored by an older build must be a no-op, not a hook that stops firing). MCP entry goes to `~/.claude.json#mcpServers.cavemem`, merged by spread so user entries survive; legacy `settings.mcpServers.cavemem` is migrated out. The `ClaudeMcpEntry` union has a stdio variant (`command`/`args`/`env`) and a remote variant `{ type: 'http', url, headers? }`; with `ctx.remote` set the entry becomes `{ type: 'http', url: '<remote.url>/mcp' (trailing slashes stripped), headers: { Authorization: 'Bearer <token>' } }` — the token is written into the config file only, never into the returned messages, and hook commands stay local either way.
- **`codex.ts`** (`capture: 'full'`, notes `no SessionEnd event`) — four events; `config.toml` round-tripped with smol-toml (`readToml`/`writeToml` return `{}` on parse failure) setting `features.codex_hooks = true` and `mcp_servers.cavemem` — in remote mode `{ url: '<remote.url>/mcp', bearer_token_env_var: CODEX_TOKEN_ENV }` (Codex reads the bearer from its own environment, so no token is ever written to the config), where `CODEX_TOKEN_ENV = 'CAVEMEM_REMOTE_TOKEN'` is exported from this module and re-exported via `index.ts`; in remote mode install also returns a message telling the user to `export CAVEMEM_REMOTE_TOKEN=<your-cavemem-remote-token>` in their shell profile — env-var name and placeholder only, the token value never appears in install output; hooks live in a dedicated `hooks.json`; SessionStart carries a `statusMessage`. Uninstall deliberately leaves `features.codex_hooks` alone (other tools may rely on it) and cleans the never-read legacy `config.json`.
- **`copilot.ts`** (`capture: 'full'`, notes `no SessionEnd event`) — Copilot hook payloads are deliberately Claude-Code-compatible so handlers need no translation. Hooks go to `~/.copilot/hooks/cavemem.json` — that directory loads every `*.json` independently, so cavemem owns a dedicated file rather than merging into a shared one; if the emptied file is cavemem-owned, uninstall deletes it. MCP goes to VS Code's *user-level* `mcp.json` (platform-specific `vscodeUserDir`, env-overridable for tests) with the root key `servers` and explicit `type: 'stdio'`.
- **`augment.ts`** (`capture: 'full'`, notes `no UserPromptSubmit event`) — Augment rejects inline command strings, so `writeWrapper` emits thin wrapper scripts (`<hookId>.sh` chmod 0755, or `.cmd` with CRLF on win32) under `~/.augment/cavemem-hooks/` that `exec` the CLI. `PostToolUse` requires a `matcher: '.*'`; `Stop` needs `metadata.includeConversationData` or the turn-summary capture would silently store nothing; session events reject a matcher. Hooks + `mcpServers` live in one `settings.json` written once; ownership detection is by wrapper-dir prefix (`isCavememGroup`).
- **`opencode.ts`** (`capture: 'full'`, notes `via bundled bridge plugin, not hooks.json`) — MCP entry `mcp.cavemem` in `~/.config/opencode/opencode.json` (honors `XDG_CONFIG_HOME`): `{ type: 'local', command: [nodeBin, cliPath, 'mcp'], enabled: true }` by default, or `{ type: 'remote', url: '<remote.url>/mcp', headers: { Authorization: 'Bearer <token>' }, enabled: true }` in remote mode (token in the config file only, never in messages); symlinks `opencodeBridge.js` from the CLI install dir into `plugins/cavemem.js` (removing a stale link first) and lists `file://./plugins/cavemem.js` in the `plugin` array so auto-load survives plugin-dir overrides; migrates the stale `mcpServers` key a prior version wrote and cleans legacy `~/.opencode/config.json`.
- **MCP-only installers** (`capture: 'none'`) — `gemini-cli.ts` (`~/.gemini/settings.json`), `cursor.ts` (`~/.cursor/mcp.json`), `antigravity.ts` (`~/.gemini/config/mcp_config.json`), `bob.ts` (`~/.bob/mcp.json`): all are the same minimal deepMerge-in / delete-out pattern; antigravity and bob additionally return an explicit query-only WARNING string so users know these IDEs never capture.
- **`windows-sh.ts`** — `checkWindowsSh({ platform?, resolveSh? })` returns the multi-line `WINDOWS_SH_MISSING_WARNING` (plain text for colorizing/asserting) when `sh` is missing on win32, else `null`; `resolveShDefault` probes with `spawnSync('sh', ['-c', 'exit 0'], { stdio: 'ignore', windowsHide: true })`. Both options are injectable so non-Windows CI can exercise the win32 branch without shelling out.

## Flow

Every hook-writing installer follows the same sequence: read current config (fallback `{}`) → filter out prior cavemem entries (idempotency) → append fresh entries naming `nodeBin cliPath hook run <id> --ide <id>` → `deepMerge`/preserve user content → single `writeJson`/`writeToml` → return progress messages. Only the MCP entry differs between modes — remote mode swaps the stdio spawn for the per-IDE URL shape above; hook registrations are identical. Uninstall mirrors it: strip cavemem entries, delete emptied keys (or the cavemem-owned file), report.

## Integration

- Consumed by `apps/cli` via `getInstaller` / `installers` from `registry.ts` and `checkWindowsSh` from `windows-sh.ts` (doctor/status health checks); the CLI's `install` command sets `ctx.remote` from the resolved remote target when `settings.remote.url` is configured, and refuses to install when `remote.url` is set but `remote.token` is empty.
- The commands these modules write into IDE configs are the runtime bridge to `apps/cli` → `@cavemem/hooks#runHook`; `opencode.ts` additionally symlinks `opencodeBridge.js` shipped from the CLI package.
- Depends on `@cavemem/config` and `smol-toml` only; tested by `test/installers.test.ts` with injected temp contexts, including a "remote mode MCP entries" suite that asserts each IDE's remote MCP shape, the codex export hint, that no install message contains the token value, and that re-installing without `remote` flips the entry back to stdio.
