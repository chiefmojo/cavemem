# packages/hooks/src/

## Responsibility

The package's entire implementation: the public export surface (`index.ts`), the mode-aware hook dispatcher (`runner.ts`), the remote-mode HTTP client (`remote.ts`), the local spool/replay queue (`spool.ts`), the worker-daemon handoff (`auto-spawn.ts`), and the shared hook I/O contracts (`types.ts`). Handler implementations live one level down in `handlers/`.

## Design

- **`index.ts`** is a flat re-export barrel — nothing but `export` statements, no logic. Consumers get exactly: `runHook`, `ensureWorkerRunning`, the remote client (`postHook`, `remoteTarget`, `RemoteAuthError`, `RemoteTarget`), the spool API (`spoolPath`, `spoolDepth`, `appendSpool`, `drainSpool`, `SpoolEntry`), the five handlers, and the three types.
- **`runner.ts`** owns the mode dispatch plus everything handlers should not care about. It first stamps `metadata.host` (from `os.hostname()`) when the caller did not supply one, then routes: an injected `RunHookOptions.store` is dispatched directly (the runner neither constructs nor closes the store and skips the spawn); otherwise settings are loaded and `remoteTarget(settings)` decides — a non-null target delegates to the private `runRemote`, which never opens a local store and never throws; a `null` target falls through to local mode with a `MemoryStore` at `<dataDir>/data.db`. Shared concerns live here: settings loading, timing (`performance.now()` → rounded `ms`), the post-hook `ensureWorkerRunning` call (local mode only, skipped for `session-end`), and error capture into `HookResult { ok: false, error, ms }`.
- **`remote.ts`** is the remote-mode client with no I/O beyond a single fetch. `remoteTarget` maps `settings.remote` to `RemoteTarget { url, token, timeoutMs }` — `null` in local mode — and `canonicalRemoteUrl` accepts only an http(s) origin with no path, query, or fragment. `postHook` performs one bearer-authenticated JSON POST to `api/hooks/:event`, aborts via `AbortController` at `remote.timeoutMs`, returns the server's `HookResult`, and throws typed errors the caller must distinguish: `RemoteAuthError` on 401 (a replay would fail identically, so never spool), `RemotePermanentError` on other 4xx (retrying is pointless), a plain `Error` otherwise.
- **`spool.ts`** is the best-effort durability queue for hook payloads that could not be delivered remotely: JSONL at `<dataDir>/spool.jsonl` (`spoolPath`), entries `{ name, input, ts }` (`SpoolEntry`). `appendSpool` appends one line under the lock, rewriting the file to drop the oldest entries past `SPOOL_CAP` (500) — durability is deliberately best-effort. `drainSpool` replays up to `SPOOL_DRAIN_MAX` (10) entries oldest-first within an optional `budgetMs` deadline (the runner passes `timeoutMs * 2`), stops at the first transient send failure, and rewrites the file with the un-sent remainder; it discards two classes of unsendable rows with a structured stderr line: malformed JSON, and `RemotePermanentError` rejections (permanently rejected entries are never retried). Locking is an exclusive-create (`wx`) `<spool>.lock` file holding the writer pid: `EEXIST` defers the operation (logged, no waiting); if the pid write fails after a successful create the lock's binding is uncertain, so the descriptor is closed but the path is deliberately *not* unlinked — locks are never auto-reclaimed, because another actor may hold a live lock, so manual clearing may be required.
- **`auto-spawn.ts`** keeps the probe path allocation-free and branch-light: `settings.remote.url` (remote mode's store lives on another machine — never start a local worker) → `CAVEMEM_NO_AUTOSTART` → `embedding.autoStart` → `provider !== 'none'` → pidfile stat → `isAlive(pid)` via `process.kill(pid, 0)` → `resolveCli()` from `process.argv[1]`. Only the miss path pays the `spawn` cost, and it is `detached` + `unref` + `stdio: 'ignore'` + `windowsHide: true` (Windows can't exec a raw `.js` path directly, hence `process.execPath <cli>`; `windowsHide` prevents a console window flashing from the detached child).
- **`types.ts`** defines `HookInput` as a *union of fields* rather than a strict schema: Claude Code's payload names (`tool_name`, `tool_response`, `last_assistant_message`, `transcript_path`, `permission_mode`, `source`, `reason`, `prompt`) coexist with legacy aliases (`tool`, `tool_output`, `turn_summary`) so non-Claude-Code IDEs and tests drive the same handlers without payload translation. `ide` is not sent by Claude Code itself — the installer wires `--ide claude-code` into the hook command and the CLI injects it before handlers run. `metadata` is a free-form record the runner stamps with `host` before dispatch. `HookResult` carries `ok` / `ms` / optional `context` (injected prompt text) / optional `error`.

## Flow

- `runHook(name, input)` stamps `metadata.host` → injected store: dispatch directly; otherwise load settings and resolve the remote target → **remote**: `runRemote` (missing token or invalid target → structured `{ remote: true }` stderr line + fail-open `ok: true`; `postHook`; on success `drainSpool` replays up to 10 spooled entries; 401 → log without spooling; any other failure → attempt `appendSpool`, then fail-open `ok: true`) → **local**: switch over the five `HookName` values (`sessionStart` / `userPromptSubmit` return `context`, the rest return void) → `ensureWorkerRunning` (unless `session-end`) → `HookResult`.
- Timing is measured around the whole dispatch, so `HookResult.ms` reflects the full handler (or remote round-trip) duration — the number the 150 ms p95 budget is judged against.
- `finally` closes the store only when the runner owns it.

## Integration

- `runner.ts` imports the five handlers from `./handlers/` plus `remote.ts` and `spool.ts`; handlers never import `runner.ts` (no cycles).
- Types in `types.ts` are the lingua franca between `apps/cli` (which parses argv + stdin into `HookInput`), `packages/installers` (whose generated hook commands must match what the CLI expects), `apps/worker` (which re-dispatches a POSTed `HookInput` through the same `runHook` with its own injected store), and the tests.
- Depends on `@cavemem/config` (`loadSettings`, `resolveDataDir`, `settings.remote`) and `@cavemem/core` (`MemoryStore`).
